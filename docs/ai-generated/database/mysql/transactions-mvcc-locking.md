# MySQL 数据库并发控制学习笔记：事务、MVCC、锁与并发问题

## 1. 并发控制的核心问题：多个事务同时操作数据

数据库并发控制主要解决：

-   多个事务同时读取数据
-   多个事务同时修改数据
-   一个事务修改时，其他事务应该看到什么

一个重要区分：

-   **单条 SQL 的原子性**
-   **多条 SQL 组成的业务操作的原子性**

------------------------------------------------------------------------

## 2. 单条 SQL 与业务原子性

例如：

``` sql
UPDATE product
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
```

这条 SQL 可以看成一个整体：

    检查 stock > 0
            ↓
    stock = stock - 1

数据库不会让另一个事务插入到这两个步骤之间。

但是：

``` sql
SELECT stock FROM product WHERE id = 1;

-- 应用层判断

UPDATE product SET stock = 0 WHERE id = 1;
```

虽然逻辑上也是：

    查询
    ↓
    判断
    ↓
    修改

但中间存在时间窗口，其他事务可能插入。

因此：

> 能让数据库一次完成的"判断 + 修改"，尽量不要拆成多个独立操作。

------------------------------------------------------------------------

## 3. 普通 SELECT 与 UPDATE 的区别

### 3.1 普通 SELECT：快照读

普通：

``` sql
SELECT balance
FROM account
WHERE id = 1;
```

通常属于快照读。

特点：

-   不一定读取最新物理数据
-   不一定因为别人修改而等待
-   根据事务可见性规则读取某个版本

------------------------------------------------------------------------

### 3.2 UPDATE：当前读

例如：

``` sql
UPDATE account
SET balance = balance + 100
WHERE id = 1;
```

它需要：

1.  找当前数据
2.  修改当前数据

因此属于当前读。

当前读需要面对最新状态，并且需要锁。

------------------------------------------------------------------------

## 4. 丢失更新问题

例子：

初始：

    stock = 1

两个事务：

    事务 A:
    读取 stock = 1

    事务 B:
    读取 stock = 1

两个事务都计算：

    1 - 1 = 0

最后：

    A 更新 stock = 0
    B 更新 stock = 0

数据库结果：

    stock = 0

但是实际：

    卖出了两件商品

问题：

> 两个事务都基于同一个旧值进行了业务计算。

解决思路：

使用数据库原子操作：

``` sql
UPDATE product
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
```

或者：

``` sql
SELECT ... FOR UPDATE
```

先锁住数据。

------------------------------------------------------------------------

## 5. 快照读与当前读

### 5.1 快照读

普通 SELECT：

    SELECT

读取：

> 当前事务可见的版本。

------------------------------------------------------------------------

### 5.2 当前读

以下属于当前读：

``` sql
SELECT ... FOR UPDATE

UPDATE

DELETE
```

读取：

> 最新真实数据，并且通常需要锁。

------------------------------------------------------------------------

### 5.3 易错点

错误理解：

> 普通 SELECT 看到的数据就是数据库当前真实值。

实际：

普通 SELECT 看到的是：

    符合当前事务可见性的版本

不一定是最新物理版本。

------------------------------------------------------------------------

## 6. MVCC 基本思想

MVCC：

Multi-Version Concurrency Control

核心：

> 不直接丢弃旧版本，而是保留版本信息，让不同事务看到不同的数据版本。

不是：

    每个事务保存一份完整数据

而是：

    当前数据版本
    +
    undo log 保存的历史信息
    +
    Read View 判断可见性

------------------------------------------------------------------------

## 7. undo log 与版本链

一次 UPDATE：

原始：

    balance = 1000

事务 A：

``` sql
UPDATE account
SET balance = 900;
```

可以理解为：

    当前记录：

    balance = 900
    trx_id = A
    roll_ptr
          |
          ↓

    undo log:

    旧版本:
    balance = 1000

如果之后继续修改：

    当前:

    800 trx_id=C
        |
        ↓
    undo:

    900 trx_id=A
        |
        ↓
    undo:

    1000

形成版本链。

------------------------------------------------------------------------

## 8. DB_TRX_ID 与 DB_ROLL_PTR

InnoDB 行记录中有隐藏信息：

### DB_TRX_ID

表示：

> 最后修改这个版本的事务 ID。

### DB_ROLL_PTR

表示：

> 指向 undo log 中旧版本的位置。

作用：

    当前版本
        |
        ↓
    undo log
        |
        ↓
    更旧版本

------------------------------------------------------------------------

## 9. 为什么 UPDATE 后别人还能看到旧数据？

例如：

事务 A：

``` sql
UPDATE account
SET balance = 900;
```

但没有提交。

物理上：

    当前记录:

    900

但是事务 B：

``` sql
SELECT balance;
```

可能看到：

    1000

原因：

    读取当前版本
          ↓
    判断 trx_id 是否可见
          ↓
    不可见
          ↓
    沿 roll_ptr 找 undo 版本
          ↓
    返回旧版本

关键：

> 物理当前值和某个事务看到的值不是同一个概念。

------------------------------------------------------------------------

## 10. Read View

Read View 可以理解为：

> 某个事务创建快照时，对事务状态的记录。

它帮助判断：

某个版本是否对当前事务可见。

------------------------------------------------------------------------

### 可见性基本规则

简化理解：

1.  自己事务产生的版本

```{=html}
<!-- -->
```
    可见

2.  创建快照之前已经提交的事务产生的版本

```{=html}
<!-- -->
```
    可见

3.  创建快照时还未提交的事务产生的版本

```{=html}
<!-- -->
```
    不可见

4.  创建快照之后才开始的事务产生的版本

```{=html}
<!-- -->
```
    不可见

不可见时：

    沿 undo log 找更早版本

------------------------------------------------------------------------

## 11. m_ids、up_limit、low_limit

Read View 中有事务 ID 信息。

### m_ids

表示：

> 创建 Read View 时仍然活跃的事务 ID。

例如：

    m_ids = [103,105,108]

表示这些事务当时还没有完成。

------------------------------------------------------------------------

### 为什么还需要边界？

因为：

只靠 m_ids 不够。

例如：

    90 不在 m_ids
    120 不在 m_ids

无法判断：

-   90 是否已经提交
-   120 是否后来才开始

所以需要范围。

------------------------------------------------------------------------

### up_limit

表示活跃事务中的较小事务 ID。

作用：

    trx_id < up_limit

    一定可见

------------------------------------------------------------------------

### low_limit

表示创建 Read View 时未来事务的边界。

作用：

    trx_id >= low_limit

    一定不可见

------------------------------------------------------------------------

中间区域：

    up_limit ~ low_limit

需要查询：

    m_ids

判断。

------------------------------------------------------------------------

## 12. REPEATABLE READ 与 READ COMMITTED

### READ COMMITTED

特点：

每次快照读重新创建 Read View。

例如：

    第一次 SELECT
    1000

    别人提交修改

    第二次 SELECT
    900

可能出现不可重复读。

------------------------------------------------------------------------

### REPEATABLE READ

MySQL InnoDB 默认隔离级别。

特点：

同一个事务尽量复用同一个 Read View。

例如：

    第一次 SELECT
    1000

    别人提交修改

    第二次 SELECT
    1000

------------------------------------------------------------------------

## 13. 不可重复读与幻读

### 不可重复读

关注：

> 同一行数据变化。

例如：

第一次：

    balance = 1000

第二次：

    balance = 900

------------------------------------------------------------------------

### 幻读

关注：

> 满足条件的数据集合变化。

例如：

第一次：

    Alice
    Bob

第二次：

    Alice
    Bob
    Carol

多出一行。

------------------------------------------------------------------------

## 14. 锁机制

### X Lock（排他锁）

用于修改。

例如：

``` sql
UPDATE account
SET balance = 900
WHERE id = 1;
```

拿到 X Lock。

特点：

    X + X
    冲突

两个事务修改同一行：

    事务 A:
    持有 X Lock

    事务 B:
    请求 X Lock

    等待

------------------------------------------------------------------------

### S Lock（共享锁）

表示共享读取。

关系：

  已有锁   请求 S   请求 X
  -------- -------- --------
  S        允许     冲突
  X        冲突     冲突

------------------------------------------------------------------------

## 15. SELECT FOR UPDATE

例如：

``` sql
SELECT *
FROM account
WHERE id = 1
FOR UPDATE;
```

含义：

> 我要基于这个数据继续修改，所以先锁住。

特点：

-   当前读
-   获取 X Lock
-   锁持续到事务结束

------------------------------------------------------------------------

事务：

``` sql
BEGIN;

SELECT ... FOR UPDATE;

UPDATE ...;

COMMIT;
```

后续 UPDATE 不需要重新等待自己的锁。

------------------------------------------------------------------------

## 16. 锁的生命周期

InnoDB 行锁通常持续：

    BEGIN
     ↓
    获取锁
     ↓
    执行操作
     ↓
    COMMIT / ROLLBACK
     ↓
    释放锁

不是 SQL 执行结束立即释放。

------------------------------------------------------------------------

## 17. 行锁与索引

InnoDB 的行锁实际上锁的是：

> 索引记录。

如果通过主键：

    主键索引
    id=1

定位数据。

如果通过普通索引：

    二级索引
    username='Alice'
            |
            ↓
    主键 id
            |
            ↓
    完整数据

二级索引不仅仅是导航，也可能参与锁。

------------------------------------------------------------------------

## 18. 死锁

死锁：

> 两个事务互相等待对方释放资源。

例：

    事务1:
    锁 A
    等待 B


    事务2:
    锁 B
    等待 A

形成：

    事务1 → 等待事务2
    事务2 → 等待事务1

解决：

-   保持统一加锁顺序
-   数据库检测死锁并回滚一个事务

------------------------------------------------------------------------

## 19. 本次学习中的重要误区

### 误区 1：快照读是不是读取复制的数据？

不是。

更准确：

    当前版本
    +
    undo log 版本链
    +
    Read View 判断

构造出事务看到的版本。

------------------------------------------------------------------------

### 误区 2：UPDATE 修改后，COMMIT 才真正修改数据？

不是。

UPDATE 时当前记录已经变化。

COMMIT：

> 确认修改正式生效。

undo log 主要用于：

-   回滚
-   构造旧版本

------------------------------------------------------------------------

### 误区 3：有锁后所有 SELECT 都不能读？

不是。

普通 SELECT：

    快照读

通常不需要等待。

只有：

    SELECT FOR UPDATE
    UPDATE
    DELETE

这类当前读需要竞争锁。

------------------------------------------------------------------------

## 20. 当前学习到的整体模型

最终可以形成：

    事务
     |
     +----------------+
     |                |
    快照读            当前读
     |                |
    MVCC             锁
     |                |
    Read View        X/S Lock
     |
    undo log
     |
    版本链

数据库并发控制的核心思想：

    普通读取：
    尽量不阻塞，提高并发

    修改操作：
    必须保证一致性，使用锁

    多个 SQL：
    使用事务组合成业务原子操作
